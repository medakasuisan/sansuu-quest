## 2. 反直感な発見（ここが設計の分かれ目）

### 発見① base64 の膨張は、圧縮でほぼ回収されている

base64 はバイナリを 1.333 倍に膨らませる（実測も理論値ぴったりの 1.333x）。
「だから外部ファイル化すれば 1.65MB → 1.18MB に減る」と考えたくなるが、**brotli がその冗長性をほぼ食い切っている**。

```
埋め込みのまま brotli   : 1.24 MB
画像を外部化した場合の合計: 画像 1.18 MB + HTML 約 50 KB(br) ≒ 1.23 MB
```

→ **画像を外部ファイルにしても「初回の総転送量」はほとんど変わらない。**
目的③（配信サイズを削る）は、**外部化そのものでは達成できない**。効くのは後述の「遅延読込」と「キャッシュ分離」のほう。

### 発見② いま本当に損しているのは「コードを1文字直すと画像1.18MBが道連れ」

`ETag` は正しく効いていて、**無変更なら再訪は 304（0バイト）**。ここは健全。
問題は**単一ファイル＝キャッシュ単位が1つ**であること。

```
現状: index.html を1文字直す → ETag 変化 → 無変更の画像46枚 1.18MB も丸ごと再ダウンロード
```

`max-age=0, must-revalidate` なので毎回必ず再検証が走り、コード変更のたびに子どもの端末が **1.24MB を再取得**する。
週1回コードを直すなら、週1回 1.24MB。**画像を別ファイルに切り出して長期キャッシュを効かせれば、コード修正時の転送は 50KB 程度に落ちる。**

### 発見③ 「オフライン完全動作」は現状 保証されていない可能性が高い

§0 は「オフライン・広告ブロッカー環境でも**ゲームは完全動作すること**」と定めているが、実測では:

- **Service Worker なし**（`serviceWorker` 参照ゼロ）
- **manifest なし**（`<link rel="manifest">` なし。あるのは favicon / apple-touch-icon のみ）
- `cache-control: must-revalidate` は「再検証できないときに古いキャッシュを出すこと」を**明示的に禁止**する指示

つまり base64 埋め込みが担保しているのは「**外部画像リクエストが遮断される環境（広告ブロッカー・画像ブロック）でも絵が出る**」ことであって、**機内モードからの起動**までは担保できていないと見られる。

> ⚠️ これは HTTP ヘッダからの推論で、**実機での機内モード起動テストは未実施**。ブラウザによっては must-revalidate を無視してオフライン時に stale を返す実装差があるため、断定はしない。
> **リファクタの前に、実機（タブレット）を機内モードにして起動できるか 1 回試すべき。** ここの答えで案の評価が変わる（→ §7 未確認事項 U1）。

## 5. 推奨: 案B（画像外部化 + 遅延読込 + キャッシュ分離）

### 5-1. 到達点

> ⚠️ **2026-07-27 追記・数字の訂正**: SW でのプリキャッシュを含めることが確定したため、初期案に書いた「初回転送 1.24MB → 250KB」は**そのままでは成立しない**。
> オフラインを退化させないには**全46枚を先読みしてキャッシュに置く**必要があり、**初回の総転送量は今とほぼ同じ**になる。改善するのは「総量」ではなく「**遊べるようになるまで**」と「**2回目以降のコスト**」。以下は訂正後の数字。

```
index.html    1.86 MB → 約 246 KB（実コードのみ・2026-07-27 実装後の実測 251,891 bytes）
img/          46枚の .webp（合計 1.18 MB・immutable な長期キャッシュ）

初回・遊べるまで  1.24 MB → 約 250 KB   ← HTML + 起動時に要る画像2枚。ここが体感の改善
初回・総転送量    1.24 MB → 約 1.24 MB  ← 残り44枚をSWがバックグラウンドで先読み（変化なし）
コード修正時      1.24 MB → 約  50 KB   ← 画像は immutable なので再取得ゼロ。ここが最大の改善
2回目以降(無変更)      0 B  →      0 B   ← 現状も304で0バイト。変化なし
```

**正直に言うと、目的③「配信サイズを削る」で実際に効くのは「コード修正時の 1.24MB → 50KB」であって、初回の総量は減らない。**
初回総量まで削るなら「物語シーンは到達時に取りに行く（オフライン時は絵なしで進行）」という**オフライン品質を落とす判断**が要る。§0 の「完全動作」を守る限り、初回総量は削れない。→ §9-2 で判断を仰ぐ。

### 5-2. 設計

**(a) 画像の配置**
`img/` を新設し、`GUIDE_IMG` / `SCENE_IMG` / `MONSTER_PNG` の WebP を実ファイルとして置く。
`assets/`（原本PNG・95ファイル）は**今まで通り `.vercelignore` で配信対象外のまま**。`img/` は配信対象に含める。

**(b) 差し替え口は維持する**
定数名（`GUIDE_IMG` / `SCENE_IMG` / `MONSTER_PNG`）と参照箇所（`.src` 代入5箇所）の**形は変えない**。中身を base64 文字列から URL 文字列に変えるだけ。

```js
// before
const SCENE_IMG = { s01: 'data:image/webp;base64,UklGR...', ... };
// after
const SCENE_IMG = { s01: 'img/s01.webp', ... };
```

→ 呼び出し側 `bg.src = SCENE_IMG[def.scene]` は**一文字も変わらない**。これが本案のリスクが小さい最大の理由。

**(c) 遅延読込とプリロード**
- 起動時に必要なのは `GUIDE_IMG` と**相棒1体の `MONSTER_PNG`** のみ（→ U2 で実装確認）。この2枚は `<link rel="preload">` で先読み
- 残り44枚はブラウザ標準の遅延取得に任せる（`img.src` 代入時に初めて取得される＝現在の表示タイミングと一致）
- **物語シーンは「次の1枚」だけ先読み**しておくと、タップ送りで絵が遅れて出る事故を防げる

**(d) キャッシュヘッダ**
`vercel.json` を新設し、`img/` 配下に長期キャッシュを付ける。

```
img/*.webp → Cache-Control: public, max-age=31536000, immutable
index.html → 現状維持（max-age=0, must-revalidate）
```

画像は内容が変わったら**ファイル名を変える**運用にする（差し替え時は新ファイル名で追加）。

**(e) オフライン担保: Service Worker（U1 の結果により採用確定・2026-07-27）**

実機で機内モード起動が動くという回答を得たため、**外部化で退化させないこと**が要件になった。vanilla・依存ゼロ・約50行の `sw.js` を新設する。

**キャッシュ戦略（リソース種別で分ける・ここを間違えると事故る）**

| 対象 | 戦略 | 理由 |
|---|---|---|
| `img/*.webp` | **cache-first** | 内容不変（差し替えは新ファイル名）。取りに行く必要がない |
| `index.html` | **network-first（フォールバック cache）** | ⚠️ **最重要**。cache-first にすると古いコードが子どもの端末に張り付いて更新が届かなくなる。オンラインなら必ず最新、オフラインならキャッシュ |
| それ以外（favicon 等） | 素通し | 影響なし |

**プリキャッシュ**
- `install` で `index.html` + 起動時2枚を**同期的に**キャッシュ（ここが失敗したら install 失敗＝旧SWのまま。安全側）
- 残り44枚は `install` 完了後に**バックグラウンドで順次**取得（失敗しても install は成功扱い。ネットワークが細い環境で初回起動を人質に取らない）

**更新の安全弁（SW最大のリスクへの対策）**
```js
self.addEventListener('install',  e => self.skipWaiting());   // 新SWを待たせない
self.addEventListener('activate', e => e.waitUntil(
  caches.keys().then(ks => Promise.all(
    ks.filter(k => k !== CACHE_NAME).map(k => caches.delete(k))  // 旧キャッシュを確実に破棄
  )).then(() => self.clients.claim())                            // 即座に制御を奪う
));
```
- `CACHE_NAME` にバージョン文字列を持たせ、**デプロイのたびに更新する**（更新忘れ防止のため、値の由来を `sw.js` 冒頭にコメントで明記する）
- **GA4 の `/g/collect` は SW を通さない**（`fetch` ハンドラで `location.origin` 以外は素通し）。計測を壊さない

**検証（§3 の必須検証に追加する項目）**
1. 機内モードで起動 → **物語シーン・図鑑・相棒すべて絵が出る**
2. コードを1文字変えて再デプロイ → **リロード1回で新しいコードが反映される**（古い版が張り付かないこと。SW事故の本丸）
3. DevTools Application → Cache Storage に旧世代のキャッシュが残っていないこと
4. 計測イベントが従来どおり `dataLayer` に乗ること（§4）

> ⚠️ SW は「入れたら終わり」ではなく**更新事故が本番で子どもの端末に固着する**タイプのリスクを持つ。上記の検証2は毎デプロイの smoke に恒久的に加えるべき（§6 デプロイ手順の改訂対象）。

### 5-3. §0 の前提の改訂差分（案Bを採る場合）

```diff
- - **単体 HTML**（`index.html` 1ファイル）。vanilla JS・依存ライブラリゼロ・ビルド工程なし
+ - **単一 HTML + 静的画像**（`index.html` + `img/*.webp`）。vanilla JS・**依存ライブラリゼロ**・**ビルド工程なし**
- - 表示画像は **base64 の WebP で HTML に埋め込み済み**（`data:image/webp` 24件）。外部画像を新規に読み込ませない
+ - 表示画像は **`img/` 配下の WebP を同一オリジンから読み込む**（46件）。**外部ドメインからは画像を読み込まない**（広告ブロッカー耐性はオリジン同一で担保）
```

※ 現規約の「`data:image/webp` **24件**」も実測 **46件** と食い違っており、いずれにせよ訂正が要る。

**維持されるもの**: 依存ライブラリゼロ / ビルド工程なし / vanilla JS / localStorage のみ / サーバー送信なし / 外部ドメイン非依存
**変わるもの**: 「1ファイル」→「1 HTML + 画像ディレクトリ」

**Phase 2 と 3 を1契約にまとめた理由**: どちらも「**表示は1ピクセルも変えず、構造だけ変える**」変更で検証軸が同一（＝画面が今と同じであることの確認）。分けると中間状態（画像を抽出したが参照は base64 のまま）が生まれ、そこには検証すべき意味がない。
逆に **Phase 4 は SW という新しい振る舞いが増える**ため検証軸が違う。ここは必ず別契約に切る。

### Tier 判定の根拠

- **セーブデータには触らない**ので §2-2 R5 の「Tier N + fixture テスト必須」には**該当しない**
- ただし Phase 3/4 は **§0 の前提（配信形態）の変更**であり、規約 §2 の「ゲーム層の構造変更」に準じる重さがあるため **Tier N（設計を先に書いて承認 → 実装）**として扱う。本文書がその「先に書く設計」にあたる
- 実装は §8 に従い **`sansuu-quest-implementer`（さんすう実装係）へ委譲**する。設計・Tier判定・承認取得・commit / push は委譲しない

## 7. リスクと安全弁

| リスク | 深刻度 | 対策 |
|---|---|---|
| 画像抽出でバイトが壊れる | 高 | Phase 2 で**抽出前後の SHA-256 一致**を機械検証。目視しない |
| 差し替え漏れ（1枚だけ古い参照が残る） | 中 | 抽出後に `index.html` 内の `data:image` **残存数がゼロ**であることを grep で機械確認 |
| オフライン/画像ブロック環境で絵が出なくなる | 中 | U1 の実測で分岐を決めてから着手（Phase 0 をゲートにしている理由） |
| 画像46リクエストで Vercel 無料枠を圧迫 | 低 | 身内利用＋ immutable 長期キャッシュで実質初回のみ。デプロイ後に実測 |
| 実装係が画像追加手順を旧手順（base64埋め込み）でやる | 中 | 規約 §5「画像を追加・差し替えるとき」を**同じターンで**書き換える（§7 の同期規律） |
| 本番で表示崩れ | 中 | ロールバックは `git revert` 1発。セーブに触らないので**子どもの進捗は revert しても無傷** |

**最大の安全弁**: 本案は**セーブデータに一切触らない**。最悪 revert しても失われるものがない。
